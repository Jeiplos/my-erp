# 库存语义 (Inventory Semantics)

## 一句话定义

库存语义指的是**「库存」这个词在跨境 ERP 里到底指哪一个数，以及这个数由谁说了算**。

一句话区分：**库存不是一个数字，而是一组语义；其中只有一个数会被推给平台。**

## 具体例子

### 一、平台分两类，库存归属完全不同

「电商平台」这个词在跨境场景里混装了两种完全不同的东西：

| | **市场型平台** | **平台仓型** |
| --- | --- | --- |
| 典型 | eBay、Walmart 3P（非 WFS）、Etsy、Shopee / Lazada 三方店铺、Temu 半托管、TikTok 半托管 | Amazon FBA、Walmart WFS、Temu 全托管、TikTok / SHEIN / AliExpress 全托管 |
| 有没有仓 | **没有仓**。货在自有仓或海外仓 3PL | 有，平台仓就是物理库位 |
| 库存谁说了算 | **系统说了算**，平台只是照着系统给的数量收单 | **平台说了算**，系统只能拉 |
| 系统能做的动作 | 推可售库存、推发货、下架 Listing | 只有两件事：**提交入仓计划**、**申请移除** |
| 主要风险 | 推少了少卖，推多了**超卖** | 平台账面与实发不符 → 差异 → **索赔** |

最容易搞错的一点：**平台仓里的货，货权依然是卖家的**。
平台是保管人，不是买家。所以那是「在本系统账上、存放在别人仓库的库存」，
是一次**库存地点转移**（自有仓 → 头程在途 → 平台虚拟仓），不是销售。

> **跨境 ERP 必须同时支持这两类平台**——不是设计者想多了，
> 而是业务本来就长这样。这就是[数据流向图](data-flow-map.md)链路 B 里
> 「三种库存语义」的由来。

### 二、三类权威源：哪些数据是自己的，哪些是别人的

比「内部数据 / 外部数据」二分更有用的分法，是按**权威源**分：

| 类别 | 谁是真源 | 具体数据 | 该怎么对待 |
| --- | --- | --- | --- |
| **内部权威** | 本系统 | SKU 与商品主数据、供应商、采购单、仓库与库位结构、自有仓实物账与流水、成本与定价策略 | 自己写，唯一真相 |
| **外部权威** | 平台 / 物流 / 税务 / 汇率源 | **平台订单**、平台仓库存、Listing 与 ASIN、结算报告与费用明细、物流轨迹、面单、汇率行情 | 只拉，落成镜像，**绝不本地手改** |
| **双权威** | 两边各一份 | **可承诺量**（系统算、平台显示）、订单状态（平台状态机 vs 本地状态机）、SKU ↔ ASIN / MSKU、价格（本地定价 vs 平台生效价） | 映射表 + 定时对账 + 差异池 |

第三类才是跨境 ERP 真正的工作量所在，也是事故多发区。

由此看清 `order` 的定位：**订单的起源在平台，`order` 不是订单的创造者**，
而是「落地 + 补齐业务语义」——补的是履约路由、占用扣减、发货、结算关联
这些平台不管的东西。

反过来，**平台完全不碰的前半段供应链**（采购、头程、调拨、盘点、海外仓入仓、补货）
才是「数据完全由系统自己处理」的部分。

### 三、库存不是一个数字

```
实物在库 (on-hand)
  − 已占用 (allocated，未发货订单预占)
  − 安全库存 (buffer，用来吸收「推送到生效」与「下单到拉单」的延迟)
  + 在途可预期到货（采购在途 / 头程在途 / 平台仓已发未上架）
  ────────────────────────────────────────────────
  = 可承诺量 ATP (available-to-promise)   ← 只有它会被推给平台
```

而平台仓那一侧，平台自己的语义还要再拆几档
（例如 Amazon 的 `Available` / `Reserved` / `Inbound` / `Unfulfillable` / `Researching`）。

> **回传给平台的从来不是「库存」，是「承诺」。**
> 平台上显示的那个数字不是事实，是本系统许下的诺言。

各家平台的字段名、时限、是否可写各不相同，一律以实际 API 为准。

### 四、运营靠什么保证平台数量正确

| # | 手段 | 解决什么 |
| --- | --- | --- |
| 1 | **单一账本** | 所有渠道的可售数都由系统算、由系统推；禁止在平台后台手改，否则系统失去真源地位 |
| 2 | **推完必须对账** | 推送成功 ≠ 平台已生效（会失败、会限流、会被拒、会被人手改），入向拉回来比对，差异进异常池 |
| 3 | **安全库存 buffer** | 「推送 → 生效」与「下单 → 被拉到」两段延迟构成的窗口期里，超卖在数学上无法避免 |
| 4 | **渠道间分配配额** | 多平台共享同一批货且**平台之间互不可见**：按比例分配 / 优先级独占 / 物理隔离 |
| 5 | **超卖兜底流程** | 超卖根除不了：拆单、换仓、延发、取消、联系买家，并触发补货 |
| 6 | **变更驱动增量回传** | 入库、出库、调拨、盘点、退货入库、订单占用，每次变动即重算并增量推送，避免全量推被限流 |
| 7 | **归零 ≠ 停售** | 推 0 只能防超卖，真要停卖必须在 Listing 层面下架——这是两件事 |

## 在本项目里怎么用

5 个服务各自持有哪一侧的数据：

| 服务 | 内部权威的数据 | 外部来的 / 镜像的数据 |
| --- | --- | --- |
| `masterdata` | 商品 / SKU、供应商、单位、定价策略、汇率（落地后算本地） | 汇率行情、**SKU ↔ ASIN / MSKU 映射的平台侧** |
| `warehouse` | 仓库 / 库区 / 库位 / **仓类型**（自有仓、海外仓、平台仓） | 纯内部 |
| `inventory` | 自有仓实物账与流水、占用、在途（本地计算） | **平台仓 / 3PL 库存 = 外部权威的只读镜像** |
| `order` | 状态机、发货单、履约路由、结算关联 | **订单本身来自平台**，`order` 是落地者不是创造者 |
| `channel` | 店铺授权、拉取游标、平台适配、原始报文留痕、回传队列与重试 | 它就是[防腐层](anti-corruption-layer.md)本体 |

**最需要提前想清楚的一处**：`inventory` 实际持有两种性质完全不同的库存——
一种是它能自由增减的事实，一种是它只能看的别人家的事实。
两者塞进一张余额表，代码里会长满 `if (warehouseType == FBA)` 这类分支。
正确做法是把「可变性」抽象成策略（可自由出库 / 只读同步 / 仅下指令），
余额表只存数量事实——详见[数据流向图](data-flow-map.md)链路 B。

另外，「占用 + 扣减」分两步不是过度设计，而正是应对
**拉单延迟 + 多平台共享库存**这两件事的最小手段：先 `allocate` 锁住，再 `ship` 真扣。

## 常见误解

- **误解一：平台是下单的地方，所以库存也归平台管。**
  市场型平台完全不碰货，库存真相只在系统手里；系统不推，平台就按旧数继续卖。

- **误解二：库存就是一个「在库数量」。**
  在库、占用、在途、安全库存、平台仓各档语义是不同的数，
  混用一个数字，补货永远算不准、超卖永远防不住。

- **误解三：推给平台了，平台就一定会照做。**
  推送会失败、会限流、会被拒；推完不对账，等于没推。

- **误解四：平台仓的库存可以本地手工调整。**
  那是只读镜像。系统对平台仓只有两个动作：提交入仓计划、申请移除。

- **误解五：多平台卖同一批货，只要「改快一点」就不会超卖。**
  平台之间互相看不见彼此的成交，必须靠配额分配、安全库存与超卖兜底流程。
