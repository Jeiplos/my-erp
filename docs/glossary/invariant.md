# 业务不变式 (Invariant)

## 一句话定义

业务不变式是**在任何时刻、任何操作之后都必须成立**的业务规则。
不是「某个流程里检查一下」，而是「永远不能违反」。

「不变式」这个词来自数学/程序验证，放在业务里意思就是：**这些条件一旦破了，数据就是错的。**

## 具体例子

ERP 里几条典型的不变式：

| 不变式 | 违反了会怎样 |
| --- | --- |
| 库存数量 ≥ 0 | 出现负库存，账实不符 |
| 销售订单至少有一条明细 | 空订单确认后无法发货 |
| 订单总额 = 各明细行金额之和 | 金额对不上账 |
| 已发货的订单不能再改明细 | 发了货还在改单，仓库和单据脱节 |
| 出库数量 ≤ 当前库存 | 超卖 |

关键在于**这些规则由谁保证**。反例（脆弱写法）：

```java
// ❌ 规则散在调用方：谁忘了检查谁就破防
if (balance.getQty() >= qty) { balance.setQty(balance.getQty() - qty); }
```

更好的写法是让对象自己守住：

```java
// ✅ 规则在对象内部，绕不过去
public void deduct(Quantity qty) {
    if (this.qty.isLessThan(qty)) {
        throw new InsufficientStockException(productId, this.qty, qty);
    }
    this.qty = this.qty.minus(qty);
}
```

## 在本项目里怎么用

每个模块开工前，先在文档里**列出该模块的不变式**，再写代码。这是本项目「文档与代码同步」原则的落点：

- 库存模块：不允许负库存；同一「商品 + 仓库」只有一条余额记录。
- 销售模块：订单必须有明细；只有已确认订单能发货；发货必须原子地扣减库存。
- 采购模块：只有已确认采购单能收货；收货必须原子地增加库存。

不变式也直接决定了**事务边界**放在哪：一次操作里同时改动的数据，必须在同一个事务里。

## 常见误解

- **误解一**：不变式就是参数校验（比如非空校验）。
  参数校验管的是「输入合法」，不变式管的是「数据状态在任何时候都自洽」。
- **误解二**：靠数据库约束就够了。数据库约束能挡住一部分（如非空、唯一），
  但跨表、带业务条件的规则（「只有已确认订单能发货」）表达不了，
  而且报错信息对用户毫无意义。**代码里必须再守一层。**
- **误解三**：只在写入时检查就行。并发下两个请求同时检查、同时通过，照样破防——
  所以库存扣减要考虑**并发控制**（乐观锁或数据库层面的条件更新）。
