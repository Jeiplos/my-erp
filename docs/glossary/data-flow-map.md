# 跨境电商 ERP 内外数据流向图

本文是词条[数据流向](data-flow.md)的配套图示，记录 my-erp 采用
`masterdata` / `warehouse` / `inventory` / `order` / `channel` 5 个业务服务之后，
系统内外的数据怎么流动。

> **术语约定**：全文的「系统」一律指 my-erp 整体，不使用第二人称。
> 本文只描述流向与通信方式，不描述字段与表结构。

## 一、坐标：四个方向

| 方向 | 含义 | 通信方式 |
| --- | --- | --- |
| **北向** | 人 → 系统 | HTTP / REST |
| **南向** | 外部系统 ↔ 系统 | HTTPS 调第三方 API（唯一的脏活区） |
| **东西向** | 系统内部服务 ↔ 服务 | **Dubbo** |
| **贯穿向** | 流经所有地方，不属于任何一层 | 时区、币种与汇率 |

南向再分入向（外部 → 系统）与出向（系统 → 外部）。

**唯一的南向出入口**是这张图最重要的一条约束：平台接口的超时、限流、
字段变更、Token 失效都被关在 `channel` 一个服务内。

## 三、南向数据流清单

### 3.1 核心节律

> **入向靠定时拉，出向靠主动推。**

推论一：`job`（定时任务）不是可选组件，它是整个系统的起搏器。
推论二：轮询必然重复拉到同一条数据，因此**幂等是生存条件，不是加分项**。

### 3.2 入向清单（外部 → 系统，全部经 channel）

| # | 数据流 | 方式 | 频率 | 落到哪 | 本轮 |
| --- | --- | --- | --- | --- | --- |
| ① | **平台订单** | 拉 | 5~15 分钟 | channel → order | 做 |
| ② | **平台 / FBA / 3PL 库存快照** | 拉 | 15~60 分钟 | channel → inventory | 做 |
| ③ | **平台结算报告** | 拉 | 每天 | channel → order（费用明细） | 简化 |
| ④ | **汇率** | 拉 | 每天 | masterdata | 做 |
| ⑤ | **物流轨迹** | 拉或推 | 小时级 | channel → order | 简化 |
| ⑥ | **平台取消 / 退款通知** | 拉 | 随 ① 一起 | channel → order | 做 |
| ⑦ | **FBA 发货计划状态** | 拉 | 天级 | channel → inventory | 简化 |
| ⑧ | **供应商报价与交期** | 人工录入 | — | masterdata | 做 |

### 3.3 出向清单（系统 → 外部，全部经 channel）

| # | 数据流 | 方式 | 触发时机 | 本轮 |
| --- | --- | --- | --- | --- |
| ⑨ | **回传发货**（单号 + 承运商） | 推 | order 发出 `OrderShipped` 事件 | 做 |
| ⑩ | **回传可售库存**（防超卖） | 推 | inventory 库存变更后 | 可后置 |
| ⑪ | **提交 FBA 发货计划** | 推 | 人工触发 | 后置 |
| ⑫ | **下物流单 / 取面单** | 推 | 发货时 | 后置（无 logistics 域） |
| ⑬ | **刊登 / 更新 Listing** | 推 | 人工触发 | 后置（无 listing 域） |
| ⑭ | **确认订单 / 标记发货** | 推 | 随 ⑨ | 做 |

**⑩ 回传可售库存值得单独说明**：这是 `channel` 存在的第二个理由。
如果不把本地可用库存回传给平台，平台会按自己的库存继续卖，直接造成超卖。
这一条把 `inventory` 与 `channel` 连成闭环，也是「本地库存」与
「平台库存」必须统一口径的原因。

## 四、五条端到端主链路

### 链路 A：平台下单 → 本地发货（第一条要跑通的链路）

```
平台          job        channel          order      inventory   masterdata/warehouse
 │             │            │                │            │              │
 │  有订单了    │            │                │            │              │
 │             │─触发①拉单─→│                │            │              │
 │←───拉取订单──│            │                │            │              │
 │             │            │ 翻译成统一模型  │            │              │
 │             │            │─Dubbo:建单────→│            │              │
 │             │            │ (幂等键 = 平台单号)           │              │
 │             │            │                │─查商品/价格/客户(Dubbo)─────→│
 │             │            │                │←─────────────────────────────│
 │             │            │                │─查可用量(Dubbo)──→│            │
 │             │            │                │←──────────────────│            │
 │             │            │                │─查仓库/库位(Dubbo)──────────→│
 │             │            │                │←─────────────────────────────│
 │             │            │                │ 履约路由：哪个仓发货？        │
 │             │            │                │─allocate 占用───→│ retries=0  │
 │             │            │                │←────成功──────────│ 写预留+流水│
 │             │            │                │ 状态 = 已确认     │            │
 │             │            │                │  [仓库拣货打包]   │            │
 │             │            │                │─ship 出库扣减───→│ retries=0  │
 │             │            │                │←────成功──────────│ 余额-、流水+│
 │             │            │                │ 状态 = 已发货     │            │
 │             │            │←──MQ: OrderShipped 事件───────────│            │
 │←─回传发货+单号│            │                │            │              │
```

此链路上有三个致命细节：

1. **`allocate` 与 `ship` 都必须 `retries=0`。**
   Dubbo 默认失败重试 2 次，不设防会把库存扣两遍。
2. **`order` 不能自己改库存**，只能调用 `inventory` 暴露的能力接口。
3. **`inventory` 永不回头调用 `order`**，需要通知就发消息事件，避免依赖成环。

### 链路 B：FBA / 海外仓库存同步（跨境电商独有）

```
job         channel           外部(FBA/3PL)      inventory
 │            │                    │                 │
 │─触发②拉库存→│                    │                 │
 │            │───库存查询 API────→│                 │
 │            │←────库存快照────────│                 │
 │            │─Dubbo: syncExternalStock()─────────→│
 │            │                    │                 │ 更新 FBA 虚拟仓余额
 │            │                    │                 │ ★ 只读同步，禁止本地手改
```

FBA 的货在平台手里，系统**无法自由出入库**，因此存在三种库存语义：

| 仓类型 | 系统能做什么 |
| --- | --- |
| 国内仓 | 自由出入库、调拨、盘点 |
| 海外仓（3PL） | 通过 3PL API 下指令，本地记影子库存 |
| **FBA 仓** | **只能同步与提交发货计划，不允许本地扣减** |

若三种语义都塞进一张余额表，代码里会长满 `if (warehouseType == FBA)` 这类分支。
**正确做法是把「可变性」抽象成策略**（可自由出库 / 只读同步 / 仅下指令），
余额表只存数量事实，行为差异交给策略决定。

「库存」到底指哪个数、又由谁说了算，见词条[库存语义](inventory-semantics.md)。

由此派生出**履约路由**问题：FBA 订单的库存扣减由平台完成，不是 `inventory` 完成。
因此链路 A 中的 `allocate` / `ship` 对 FBA 订单**必须跳过**，
只记录「已售」，等下一次库存同步时对齐。
**同一张订单表，两种履约路径**——这就是履约路由的由来。

### 链路 C：头程发货（国内仓 → 海外仓 / FBA）

```
采购到货 → 国内仓入库
   │
   ▼
建头程单：国内仓 → 在途仓          ← inventory：国内仓余额-，在途余额+
   │
   ▼
货代订舱 / 报关 / 出运             ← 无 logistics 域，本轮手工登记
   │
   ▼
目的仓签收                          ← 人工确认，或 3PL API 回传
   │  在途余额-，海外仓 / FBA 余额+
   ▼
【若目的地是 FBA】还需提前提交发货计划：
     Shipment Plan → ShipmentId → 打印外箱标 → 交运
```

这条链路的库存要跨三个虚拟仓移动：**国内仓 → 在途仓 → 海外仓 / FBA**。
因此 `warehouse` 的「仓类型」是核心概念，`inventory` 必须有「在途」这种库存状态。
**在途库存是最容易漏掉的库存**，漏了它，补货计划永远算不准。

### 链路 D：平台结算与对账（钱的入向）

```
job → channel 拉结算报告
        │
        ├─ 佣金 / FBA 配送费 / 广告费 / 仓储费 / 退款 / 汇兑
        │
        ▼
   与本地订单逐笔匹配        ← 按平台单号 + 平台交易号
        │
        ├─ 匹配上   → 记费用明细
        └─ 匹配不上 → 进入差异池（少结、漏结、多结）
```

**本轮的妥协**：项目没有 finance / settlement 域，
这条链路的终点只能是「费用明细表」。真正的应收应付、毛利核算、汇兑损益
需要独立的财务域，本轮不做。

### 链路 E：汇率（最简单，但贯穿一切）

```
job → 汇率源(API) → masterdata.currency_rate
                        │
                        └─→ order（订单币种）  inventory（成本）  channel（费用）
```

两条必须从第一天定死的规则：

1. **`JPY` / `KRW` 是 0 位小数**，把 `setScale(2)` 写死会算错钱。
   币种小数位必须是**配置**，不是魔法数字。
2. **折算规则要说清**：交易日汇率 / 月末汇率 / 结算汇率是三个不同的东西，
   分别服务成本、结算与报表。

## 五、东西向：Dubbo 调用矩阵

这张表是服务边界的落地检查表。**出现表外的调用，就说明边界画错了。**

| 调用方 | 被调方 | 方式 | 调用内容 | 关键约束 |
| --- | --- | --- | --- | --- |
| `order` | `masterdata` | Dubbo 同步 | 查商品、价格、客户、单位 | 只读 |
| `order` | `inventory` | Dubbo 同步 | 查可用量、**占用**、**出库扣减** | **`retries=0`** |
| `order` | `warehouse` | Dubbo 同步 | 查仓库、库位、履约路由规则 | 只读 |
| `channel` | `order` | Dubbo 同步 | 投递平台订单（带幂等键） | **`retries=0`** |
| `channel` | `inventory` | Dubbo 同步 | FBA / 3PL 库存同步 | 只允许写 external 类型仓 |
| `channel` | `masterdata` | Dubbo 同步 | SKU 映射、汇率 | 只读 |
| `inventory` | `masterdata` | Dubbo 同步 | **计量单位换算** | 只读，高频 |
| `inventory` | `warehouse` | Dubbo 同步 | 库位校验、仓类型策略 | 只读 |
| `order` | MQ | **发布** | `OrderCreated` / `OrderShipped` / `OrderCancelled` | — |
| `channel` | MQ | **订阅** | 消费 `OrderShipped` → 回传平台 | 幂等消费 |
| `inventory` | MQ | **发布** | `StockChanged` / `StockLow` | — |
| `job` | — | 触发 | 定时拉起 ①②③④⑦ | 分布式锁防重复执行 |

三条不能破的纪律：

1. **`inventory` 绝不调用 `order`。** 需要通知就发事件。
2. **`order` 绝不直接调平台 API。** 要回传平台就发事件给 `channel`。
3. **`channel` 不持有「订单最终状态」的决定权。**
   它只负责投递与翻译，状态由 `order` 说了算，
   否则会出现两个服务都认为自己拥有订单状态。

## 六、每个服务的数据入口与出口

| 服务 | 数据入口（谁写它） | 数据出口（谁读它） |
| --- | --- | --- |
| `masterdata` | 人工维护、Excel 导入、汇率 job、channel（SKU 映射） | order、inventory、channel、warehouse |
| `warehouse` | 人工维护 | order、inventory、channel |
| `inventory` | order（占用 / 扣减）、channel（FBA 与 3PL 同步）、仓管（盘点 / 调拨 / 头程）、采购入库（手工） | order（可用量）、channel（回传平台可售量）、报表 |
| `order` | **channel（平台单）**、人工建单、北向前端 | channel（经消息事件）、报表 |
| `channel` | job 触发、人工配置店铺授权 | order（投递订单）、inventory（库存同步） |

**自检方法**：如果发现「`inventory` 需要读 `order` 的表」，
或「`order` 需要直接写 `inventory` 的表」，说明边界破了——
回去改接口，不要改表。

## 七、两条贯穿一切的暗流

### 7.1 时间与时区

平台给的时间戳通常是 UTC，服务器在 +8，买家在其他时区，结算日按平台时区算。

- 库内统一存 **UTC**，只在展示层转时区。
- 单据的「业务日期」与「系统时间」是两个字段，不要合并。

### 7.2 币种与精度

每个金额字段都要能回答三个问题：**什么币种？几位小数？用哪个汇率算的？**

- 金额值 + 币种码 + 汇率 + 汇率日期，四个一起存，缺一个将来都算不出账。
- 币种小数位是配置，不是常数。

## 八、缺口清单

当前 5 个服务是业务内核，一套能真正跑起来的系统还需要下列部分：

| 缺口 | 影响 | 本轮处理方式 |
| --- | --- | --- |
| **采购 `purchasing`** | 库存的「入库」没有正当来源 | 用 `inventory` 的手工入库单过渡 |
| **财务 `finance` / `settlement`** | 结算、应收应付、毛利、汇兑损益做不了 | 只落费用明细表，明确标记为权宜之计 |
| **物流 `logistics`** | 面单、头程、运费试算做不了 | 手工维护发货单号与运费 |
| **`job` 定时任务** | 入向 ①②③④⑦ 全部无法触发 | **必须补**，跨境 ERP 没有它跑不动 |
| **MQ 消息** | 链路 A 的回传环节断裂，退化成同步耦合 | **必须补**，否则 `channel` 会被 `order` 卡住 |
| **Nacos** | Dubbo 找不到服务 | **必须补**（硬性依赖） |
| **HTTP 入口与认证** | 系统没有门，前端与 Postman 无法接入 | 各服务自带 Controller；认证可后置 |
| **报表 `reporting`** | 跨服务查询（如订单全链路状态）没有落点 | 暂时跨服务 Dubbo 聚合，或先不做 |

因此「最小可运行形态」是：

```
5 个业务服务（masterdata / warehouse / inventory / order / channel）
+ Nacos            （Dubbo 硬依赖）
+ MySQL            （每服务独立库，绝不共享）
+ MQ               （链路 A 需要）
+ Job              （XXL-Job，或先用 @Scheduled 起步）
+ 一个 Mock 平台服务（模拟 Amazon / Shopee，解决无真实数据的问题）
+ 每个服务一个 @RestController（充当北向的门）
```

## 九、建议推进顺序

| 阶段 | 内容 | 理由 |
| --- | --- | --- |
| 0 | Nacos + 5 个空服务互相 Dubbo 调通 | 先证明这个「群」能跑 |
| 1 | `masterdata` + `warehouse`（含仓类型） | 一切的前置，先把「名词」定下来 |
| 2 | `inventory`：余额 + 流水 + 占用/扣减 + 防超卖 | 内核，技术含量最高 |
| 3 | `order`：订单 + 状态机 | 把阶段 1 与 2 串起来 |
| 4 | `channel` + **Mock 平台**：拉单 + 回传发货 | 闭合成链路 A，系统第一次「活」过来 |
| 5 | 补齐 Job + MQ，链路 A 全自动 | 从「能跑」到「像个真系统」 |
| 6 | FBA / 3PL 库存同步（链路 B） | 跨境电商的分水岭 |
| 7 | 头程（链路 C）、结算明细（链路 D）、汇率（链路 E） | 补全跨境特征 |

**关键点：阶段 4 之前系统是「死」的；跑通链路 A，它才第一次像 ERP。**

## 十、待决问题

以下问题没有标准答案，取决于项目要练到哪一层：

1. 链路 A 中「占用」与「扣减」分两步，是否过度设计？
   （这决定系统有没有真正的防超卖能力）
2. 履约路由（哪个仓发货）的规则该放在 `order` 还是 `warehouse`？
3. FBA 订单「跳过 allocate / ship」的设计，会不会让订单状态机变得别扭？
4. 平台结算明细在没有财务域时，该挂在 `channel` 还是 `order`？
