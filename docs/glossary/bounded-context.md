# 限界上下文 (Bounded Context)

## 一句话定义

限界上下文是**一个词、一套模型能够自洽生效的边界**。
同一个词在不同业务范围里含义不同时，就应该划成不同的上下文，各自用自己的模型。

一句话记法：**同一个词，在不同部门嘴里说的不是一回事。**

## 具体例子

「商品」这个词在 ERP 里至少有三种含义：

| 上下文 | 「商品」关心什么 |
| --- | --- |
| 采购 | 供应商是谁、采购价、起订量、交期 |
| 销售 | 售价、折扣、能不能拆包卖、能不能搭赠 |
| 库存 | 计量单位、体积重量、存放仓库、批次 |

如果强行做一张「万能商品表」，把所有字段塞进去，结果是：

- 每个字段对某个上下文都是无关甚至误导的（采购不需要知道零售折扣）。
- 任何一方改动字段，其他方都要跟着回归测试。
- 模型越来越臃肿，最后没人敢改。

正确做法是**各自建模**，通过明确约定的 ID 关联：

```
采购上下文 Goods    ── productId ──▶  销售上下文 Product
（含供应商、交期）                     （含售价、折扣）
        └──────── productId ───────▶  库存上下文 StockItem
                                      （含单位、仓库、批次）
```

注意：它们之间**不是继承或包含关系**，而是各自独立、
通过 `productId` 这个稳定的标识互相引用。

## 在本项目里怎么用

my-erp 的模块划分（`masterdata` / `inventory` / `sales` / `purchasing` / `reporting`）
**在理念上就是限界上下文的雏形**。

但对这个示例项目，需要明确一处务实取舍：

> **不做到「每个上下文一个独立模型」的程度。**
> 本项目让 `masterdata` 下的 `Product` 被其他模块共同引用，
> 以保持示例的可读性与代码量可控。

也就是说，本项目**借用了限界上下文的模块边界思想，但没有承担完整的多模型成本**。
等迭代到需要真正隔离时（例如引入「采购专用商品视图」），再按此词条演进。

## 常见误解

- **误解一**：限界上下文 = 微服务。两者无关。一个单体应用内部可以有多个上下文；
  一个微服务里也可能混着多个上下文。
- **误解二**：上下文之间不能共享数据。可以共享，但应共享**标识（ID）**，
  而不是共享同一套可变模型。
- **误解三**：一开始就要把所有上下文划清楚。边界是**演化出来的**，
  小项目过早划分会带来大量映射代码。本项目就是先粗后细。
