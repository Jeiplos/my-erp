# 主数据 (Master Data)

## 一句话定义

主数据是**被各个业务流程共同引用的基础数据**，它本身不描述「某一次交易」，
而是被交易反复引用的「档案」。

一句话区分：**主数据是名词档案（商品、客户），交易数据是动词记录（订单、出入库）。**

## 具体例子

| 类型 | 例子 | 特征 |
| --- | --- | --- |
| **主数据** | 商品、客户、供应商、仓库、计量单位 | 变化慢、被广泛引用、不允许随便删 |
| **交易数据** | 销售订单、采购订单、出入库单 | 持续新增、引用主数据、量大 |

两者的关键差异体现在**删除行为**上：

```
商品 SKU-1001 已被 37 张销售订单引用
   → 不能物理删除，只能"停用"（status = INACTIVE）
   → 因为历史订单必须还能查到它当时卖的是什么
```

这就是为什么主数据几乎都带一个 `status`（启用/停用）字段，
而不是提供真正的 `DELETE`。删掉主数据 = 历史单据集体变成孤儿数据。

主数据的另一个特征是**变更要可追溯**：商品改价、客户改信用额度，
往往需要留下变更记录，因为下游的金额计算都受它影响。

## 在本项目里怎么用

`masterdata` 模块是本项目实现的**第一个模块**，理由是它是其他一切的前置——
没有商品和客户，销售订单无从谈起。

MVP 阶段规划的主数据：

| 主数据 | 关键字段 | 说明 |
| --- | --- | --- |
| 商品 Product | 编码、名称、单位、状态 | 最基本的档案 |
| 客户 Customer | 编码、名称、状态 | 销售订单的对手方 |
| 供应商 Supplier | 编码、名称、状态 | 采购订单的对手方 |
| 仓库 Warehouse | 编码、名称 | 库存的归属维度 |

MVP 阶段**只做增删改查 + 停用**，不做价格版本、不做多组织、不做审批流——
那些留给后续迭代。

## 常见误解

- **误解一**：主数据就是「基础表」，随便设计。它的字段会被全系统引用，
  一处设计不当（比如把「单位」直接写成字符串）会蔓延到所有模块。
- **误解二**：主数据可以自由删除。一经引用的主数据只能停用，见上面的例子。
- **误解三**：主数据不需要业务规则。恰恰相反，「已停用的商品不能开新单」
  「商品编码不可重复」这类规则就是主数据自己的[不变式](invariant.md)。
