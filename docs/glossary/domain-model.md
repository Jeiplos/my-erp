# 领域模型 (Domain Model)

## 一句话定义

领域模型是对**业务本身的抽象表达**——把业务里的名词、规则、约束写成代码结构，
而不是把数据库表结构原样搬进代码。

## 具体例子

同样是「销售订单」，两种截然不同的建模思路：

**表驱动（不是领域模型）**：先设计 `sales_order` 表，然后生成一个 `SalesOrder` 类，
字段和表列一一对应，谁想改状态就直接 `order.setStatus("SHIPPED")`。

**领域模型**：代码里存在 `SalesOrder` 这个对象，它自己知道业务规则：

```java
// 领域模型的行为是"业务动作"，不是"改字段"
order.confirm();   // 内部会校验：草稿才能确认、必须有明细行
order.ship();      // 内部会校验：已确认才能发货
```

区别在于：**业务规则住在对象内部，而不是散落在 Service 的 if-else 里**。
这样当「未确认的订单不能发货」这条规则存在时，任何调用 `ship()` 的路径都会被拦住，
不需要每个 Service 各自记得检查一遍。

## 在本项目里怎么用

my-erp 的核心模块（`masterdata`、`inventory`、`sales`、`purchasing`）都会采用领域模型：
「订单」「库存」这些对象自带状态流转方法，业务规则尽可能写在它们身上，
应用服务只负责编排流程（见[应用服务](application-service.md)）。

## 常见误解

- **误解一**：领域模型就是实体类。实际上实体只是它的一部分，规则和行为才是重点。
- **误解二**：领域模型等于必须用 DDD 全套（聚合、领域事件、CQRS…）。
  不必。本项目只用其中最朴素的部分，够用就行。
- **误解三**：有了领域模型就不需要数据库设计了。数据库照样要设计，只是代码不再被表结构牵着走。
