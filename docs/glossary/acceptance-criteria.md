# 验收标准 (Acceptance Criteria)

## 一句话定义

验收标准是**判定「这个模块算做完了」的可检验条件**：
满足则收工，不满足则未完成。它把「差不多了」变成「是或否」。

关键在**可检验**——「代码质量好」不是验收标准，「负库存扣减会抛异常且有测试覆盖」才是。

## 具体例子

以库存模块为例，一份可用的验收清单：

**功能（正常路径）**

- [ ] 能对「商品 + 仓库」入账，余额正确增加
- [ ] 能出账，余额正确减少
- [ ] 能按商品或仓库查询当前余额

**不变式（异常路径）—— 这部分最容易被跳过，也最重要**

- [ ] 出账数量 > 当前库存时，抛出明确业务异常，且**余额未被改动**
- [ ] 出账数量为 0 或负数时被拒绝
- [ ] 不存在的商品/仓库被拒绝
- [ ] 并发两次出账不能把余额扣成负数

**工程**

- [ ] `mvn test` 全绿，不变式均有对应测试用例
- [ ] 已停用（status=INACTIVE）的商品不能参与出入账
- [ ] 领域层未 import Spring/JPA 的逻辑类
- [ ] 已在 `docs/` 补上本模块的设计说明

验收标准不是形式主义：**「异常路径的清单」实际上就是[业务不变式](invariant.md)清单的执行版**，
写一次可以在实现、测试、评审三个环节复用。

## 在本项目里怎么用

每个模块开工**之前**先写验收清单，放在该模块的设计文档里，然后再动手编码。
顺序很重要——先写清单能避免「做到哪算哪」和「测试只覆盖了顺手写的路径」。

模板（复制到每个模块文档里）：

```markdown
## 验收标准：<模块名>

### 功能
- [ ] ...

### 不变式与异常路径
- [ ] ...

### 工程
- [ ] mvn test 全绿
- [ ] 领域层无框架依赖
```

## 常见误解

- **误解一**：验收标准 = 测试用例。两者相关但不相同：
  验收标准描述**要达到什么**，测试用例是**验证手段**。先有标准，再有测试。
- **误解二**：只写正常路径就够了。经验上**异常路径才是 bug 的产地**，
  清单里不带「应该被拒绝」的条目，等于默认放开。
- **误解三**：验收标准要一次写全、永不变更。它应随认知更新，
  但变更要落在文档里（本项目要求「文档与代码同步」）。
