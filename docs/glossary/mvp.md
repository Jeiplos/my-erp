# MVP (Minimum Viable Product)

## 一句话定义

MVP（最小可行产品）是**只做能跑通核心闭环的最小功能集**：
足以验证「这条路走得通」，但不含任何锦上添花的东西。

关键词是**闭环**——不是做了一堆功能，而是有一条从头到尾走通的路。

## 具体例子

ERP 的核心闭环是什么？商品的进销存：

```
建商品 → 采购入库 → 库存增加 → 销售开单 → 发货出库 → 库存减少
```

这一条链路走通，ERP 的骨架就立住了；走不通，加再多功能也没意义。

**属于 MVP**（少一个闭环就断了）：

- 商品/客户的基础增删改查
- 采购单创建 + 收货入库
- 销售单创建 + 发货出库
- 库存余额查询

**不属于 MVP**（做不做都不影响闭环验证）：

- 多仓库、批次/序列号、保质期
- 审批流、角色权限
- 退货、换货、调拨
- 报表大屏、导出 Excel
- Redis 缓存、消息队列、分布式事务

判断口径：**「不做它，主链路还能跑通吗？」** 能 → 不属于 MVP。

## 在本项目里怎么用

你的目标是「**自己实现 MVP，再迭代添加中间件使之完整**」，
这与本词条完全一致。据此给本项目的阶段性口径：

| 阶段 | 内容 | 完成标志 |
| --- | --- | --- |
| 阶段一（MVP） | masterdata + inventory + sales + purchasing 最小闭环，存 H2 | 端到端闭环跑通，`mvn test` 全绿 |
| 阶段二（加固） | 并发扣减、事务边界、错误码、校验完善 | 边界场景有测试覆盖 |
| 阶段三（中间件） | 换 MySQL、加 Redis/消息队列、加日志与监控 | 见[中间件](middleware.md) |

MVP 阶段的**硬要求**（不可省）：
不变式校验、事务边界、分层职责、测试。

MVP 阶段的**可省项**（后续补）：
缓存、异步、分库分表、权限、美化。

> 一句提醒：MVP 削的是**功能范围**，不是**代码质量**。
> 用「反正是 MVP」当借口写出四处漏规则的代码，后面加中间件时只会更痛。

## 常见误解

- **误解一**：MVP = 半成品、能演示就行。它是**功能少但每处都做对**，
  而不是**功能多但处处将就**。
- **误解二**：MVP 要一次设计好全部扩展点。过度预留扩展点会让 MVP 变复杂，
  扩展点应该在真实需求出现时再添加。
- **误解三**：MVP 之后就不用重构了。恰恰相反，MVP 的价值就是让后续迭代有据可依，
  该调整的模型在阶段二就要调整。
