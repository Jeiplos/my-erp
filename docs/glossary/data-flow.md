# 数据流向 (Data Flow)

## 一句话定义

数据流向描述的是**数据从哪来、经过谁、到哪去**，以及跨越系统边界时走哪种通信方式。

一句话区分：**数据流向关心的是「谁把数据交给谁」，而不是「数据存在哪张表」。**

## 具体例子

先统一四个方向的叫法。本仓库文档一律使用这套术语，不再混用其他说法。

| 方向 | 指什么 | 通信方式 | 在本项目中的例子 |
| --- | --- | --- | --- |
| **北向** | 人 → 系统 | HTTP / REST | 运营在页面上新建商品 |
| **南向** | 外部系统 ↔ 系统 | HTTPS 调第三方 API | 从电商平台拉取订单 |
| **东西向** | 系统内部服务 ↔ 服务 | **Dubbo** | 订单服务调用库存服务占用库存 |
| **贯穿向** | 流经所有地方、不属于某一层 | 随数据一起存 | 时区、币种与汇率 |

南向还要再分成两个方向：

| 叫法 | 方向 | 在本项目中的例子 |
| --- | --- | --- |
| **入向** | 外部 → 系统 | 拉订单、同步 FBA 库存、拉结算报告、拉汇率 |
| **出向** | 系统 → 外部 | 回传发货、回传可售库存、提交 FBA 发货计划 |

由此得到一条最重要的规律：

> **入向靠定时拉，出向靠主动推。**

原因是绝大多数电商平台不提供可靠的回调通知，系统只能定时轮询；
反过来，系统要告诉平台「已发货」，就必须主动调平台的接口推过去。

这条规律有两个直接推论：

1. **定时任务不是可选组件**，它是整个系统的起搏器——入向数据全靠它驱动。
2. **入向数据的落地必须幂等**，因为轮询必然重复拉到同一条记录。

## 在本项目里怎么用

本项目采用 5 个业务服务，南向流量由 `channel` 一家独占：

| 服务 | 在南向数据流中的角色 |
| --- | --- |
| `channel` | **唯一的南向出入口**：所有对平台的调用都写在这里 |
| `order` | 通过 Dubbo 接收 `channel` 投递的订单；只发消息事件，不直接调平台 |
| `inventory` | 通过 Dubbo 接收 `channel` 同步的 FBA / 海外仓库存 |
| `masterdata` | 提供商品、客户、供应商、计量单位、价格、币种汇率 |
| `warehouse` | 提供仓库、库区、库位与仓类型（自有仓 / 海外仓 / FBA） |

由此得到三条不能破的纪律：

1. **南向流量只允许 `channel` 出入**——其他服务一律不许直接调平台 API。
   平台接口会超时、会限流、会改字段，把它们关在一个服务里，
   它挂了只影响数据进出的快慢，不会波及其他服务。
2. **`inventory` 不调用 `order`**——需要通知就发消息事件。
   否则 `order → inventory` 与 `inventory → order` 会形成循环依赖。
3. **跨服务写操作必须 `retries=0` 并自带幂等键**——Dubbo 默认失败重试 2 次，
   不设防会让库存被重复扣减。

## 常见误解

- **误解一：文档里的「你」和「系统」是两个不同的东西。**
  讨论时「你」指的是读者或开发者，但在描述数据流向时，
  「向平台回传发货」这类句子的主语其实是**系统本体**，不是读者。
  同一份文档里两种「你」混用，读者会分不清说的是自己还是系统。
  **本仓库的约定：描述数据流向时一律用「系统」指代 my-erp 整体，不出现第二人称。**

- **误解二：数据流向就是数据库表关系。**
  表关系回答「数据存在哪」，数据流向回答「数据怎么流动、跨越边界时用什么通信」。
  两者会不一致：`order` 与 `inventory` 之间**不允许有外键**，
  但它们之间必然有数据流（Dubbo 调用 + 消息事件）。

- **误解三：所有跨服务调用都应该用 Dubbo。**
  同步的查询和命令用 Dubbo；「某件事已经发生」的通知用消息事件。
  把通知也做成同步调用，既会让 `channel` 被 `order` 卡住，也会让服务依赖成环。

- **误解四：入向数据能拉到就一定准。**
  轮询会重复拉到同一条记录，所以入向数据落地**必须幂等**
  （例如用平台单号作唯一键）。幂等不是加分项，是入向数据的生存条件。
