# 中间件 (Middleware)

## 一句话定义

中间件是**位于应用程序与操作系统/网络之间、被多个应用共用的基础组件**，
用来解决应用自身难以优雅解决的共性问题：缓存、消息、事务、注册发现、网关等。

关键判断：**它是「基础设施能力」，不是「业务功能」。**

## 具体例子

ERP 里几个典型场景，以及它们分别对应哪类中间件：

| 场景 | 不用中间件 | 用中间件 |
| --- | --- | --- |
| 商品详情每次查数据库 | 数据库压力大、响应慢 | **Redis** 缓存，读走内存 |
| 发货后要发短信+记日志+推报表 | 同步调用，一处慢全链路慢 | **消息队列**（RabbitMQ/Kafka）异步解耦 |
| 多个实例同时部署，定时任务重复执行 | 任务跑多遍、数据重复 | 分布式锁（Redis/ZooKeeper） |
| 服务拆成多个进程 | 硬编码 IP，改地址要重新发版 | **注册中心**（Nacos/Consul） |
| 外部流量统一鉴权限流 | 每个服务各写一遍 | **API 网关** |

注意每一项的共性：**都是横切关注点**，与「订单怎么算钱」这类业务规则无关。
这也是为什么中间件适合在 MVP 跑通之后再引入——它们不改变主链路，只改变运行方式。

## 在本项目里怎么用

按你的计划，中间件属于**阶段三**。对应的落地路径：

| 顺序 | 引入什么 | 解决的问题 | 触发时机 |
| --- | --- | --- | --- |
| 1 | 换 MySQL（严格说不算中间件，但是必要一步） | H2 数据不持久、不适合真实使用 | MVP 闭环跑通后 |
| 2 | Redis 缓存 | 主数据（商品/客户）被高频读取 | 出现明显重复查询时 |
| 3 | 消息队列 | 发货后的通知、报表等异步动作 | 出现「一个操作要干好几件事」时 |
| 4 | 分布式锁 | 定时任务/并发扣减的多实例场景 | 真的部署多实例时 |

**引入顺序的原则：先有痛点，再上组件。**
没有痛点就引入，只会得到更复杂的部署和更多故障点。

同时要意识到中间件带来的**新复杂度**（这也是它的代价）：

- 缓存 → 一致性问题（缓存与数据库不同步）
- 消息队列 → 消息丢失、**重复消费**（消费端必须做到幂等：同一条消息处理多次，结果与处理一次相同）
- 分布式锁 → 锁超时、死锁、性能瓶颈

## 常见误解

- **误解一**：中间件越多越显专业。每多一个组件就多一处运维与故障面，
  小项目加满中间件通常是负收益。
- **误解二**：数据库连接池、日志框架也算中间件。
  它们通常算**库/框架**，不额外部署进程；中间件一般指独立运行的基础服务。
- **误解三**：先用上再说，以后不好再拆。中间件会改变代码结构
  （比如异步化要求业务能容忍最终一致），后补的改造成本远高于按需引入。
