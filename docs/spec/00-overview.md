# ERP 规格文档 · 总览

## 1. 范围

本文档描述一个用 Java 复现的简单 ERP 示例服务，采用微服务架构，按业务模块拆分为 5 个服务：

- **masterdata**：商品、客户、供应商、仓库等主数据
- **inventory**：库存余额、预占、流水、入库、出库、调整
- **sales**：销售订单、确认、部分发货、发货、取消
- **purchasing**：采购订单、确认、部分收货、收货、取消
- **reporting**：只读报表查询

本文档为总览，各服务的详细规格见对应服务文档。

技术基线：

- Java 21
- Spring Boot 3.x
- MySQL 8，每服务独立 schema
- MyBatis-Plus + Flyway
- 服务间调用契约后续补充

## 2. 非目标

以下内容明确不在 MVP 范围内：

- 不做鉴权与权限
- 不做成本核算（移动加权平均、FIFO、标准成本等）
- 不做多币种实际结算与税率计算
- 不做单位换算的实际逻辑
- 不做退货、换货、调拨、盘点
- 不做多仓（二期）
- 不做分布式事务（留坑）
- 不做服务间调用契约（后续补充）
- 不做表结构设计（后续单独文档）

## 3. 术语表

| 术语 | 含义 |
|---|---|
| SKU | 商品最小库存单位 |
| 基本单位 | 库存记账单位，一期为单单位 |
| 现存量 on_hand | 仓库实际存在的数量 |
| 预占量 reserved | 已被订单锁定、尚未出库的数量 |
| 可用量 available | `on_hand - reserved` |
| 预占 | 订单确认时锁定库存，防止超卖 |
| 释放 | 订单取消或发货后，解除预占 |
| 流水 | 每一次库存变动的不可变记录 |
| 幂等键 | 调用方生成的唯一键，防止重复写操作 |
| 业务 key | 对外可见的唯一标识，如 SKU 编码、订单号 |
| 停用 | 逻辑删除，保留记录，不可再被新单据引用 |

## 4. 服务划分与依赖
```
masterdata ← inventory ← sales
    ↑             ↑        ↑
    └────── purchasing ────┘
            ↑
        reporting（只读，聚合查询）
```

- masterdata 不依赖其他服务
- inventory 依赖 masterdata 获取 SKU、仓库
- sales 依赖 masterdata、inventory
- purchasing 依赖 masterdata、inventory
- reporting 只读，可依赖所有服务，但建议通过只读副本或聚合查询

**禁止双向依赖。** 跨级依赖允许，但需在文档中说明原因。

数据库：每服务独立 schema，禁止跨服务直连表。  
分布式事务：暂不处理，文档留坑标记，后续解决。  
报表：纯 CRUD，后续再说。

## 5. 库存预占模型（重点）

### 5.1 为什么预占是 ERP 核心复杂性

ERP 与普通电商后台最大的区别之一：**库存不是单一数字，而是多个状态的数量叠加**。

如果没有预占，会出现：

- 两个订单同时确认，都看到库存 10，都卖出去，实际只有 10 件，导致超卖
- 订单确认后迟迟不发货，库存被占用但系统不知道
- 部分发货后，剩余数量是否还能卖，无法判断
- 取消订单时，不知道释放多少库存

预占模型把库存拆成：

| 字段 | 含义 |
|---|---|
| on_hand_qty | 实际在库数量 |
| reserved_qty | 已被订单锁定数量 |
| available_qty | 可售数量 = on_hand - reserved |

**所有销售确认、发货、取消，都必须操作这三个量。**

### 5.2 预占生命周期

```
草稿 DRAFT
│ 不预占
▼
确认 CONFIRMED
│ 逐行预占：reserved_qty += 订购数量
│ 全部成功才确认，任一行失败则整体回滚
▼
部分发货 PARTIALLY_SHIPPED
│ 发货行：on_hand_qty -= 发货数量
│ reserved_qty -= 发货数量
│ 剩余未发：继续预占
▼
全部发货 SHIPPED
│ reserved_qty 清零
▼
取消 CANCELLED（仅未发货部分）
│ 释放剩余预占：reserved_qty -= 未发数量
```

### 5.3 预占设计原则

- 预占必须可追溯：每笔预占对应订单行
- 预占必须可释放：订单取消、发货时释放
- 预占必须防重复：同一订单行不能重复预占
- 预占必须防负库存：`on_hand_qty >= reserved_qty >= 0`
- 预占不设过期时间：由订单状态驱动释放
- 预占表必须存在，否则无法表达部分发货、取消剩余等场景

### 5.4 并发策略

- 扣减和预占使用 **条件更新**：`UPDATE ... WHERE available_qty >= ?`
- 或使用 **行锁**：`SELECT ... FOR UPDATE`
- 配合乐观锁 `version` 字段
- 所有写操作必须幂等

## 6. 成本核算说明（保留但不实现）

成本核算解决：库存值多少钱、出库成本、销售毛利、期末存货资产。

常见方法：

| 方法 | 含义 | 复杂度 |
|---|---|---|
| 移动加权平均 | 每次入库重算平均成本 | 中 |
| FIFO | 先进先出，按批次成本 | 高 |
| 标准成本 | 预设标准成本，差异另算 | 高 |
| 批次成本 | 按批次/序列号核算 | 很高 |

MVP 决定：

- **不做成本核算，只做数量计算**
- 保留字段：单据行保留 `unit_price`、`amount`、`currency`
- 库存流水保留可选 `unit_cost`、`total_cost`
- 接口预留 `CostCalculator`，不实现
- 文档中说明未来可选方案

## 8. 幂等设计（重点）

### 8.1 为什么需要

- 服务间调用可能重试
- 网络超时后调用方可能重发
- 用户可能重复点击
- 消息可能重复消费

### 8.2 要求

- 所有写操作必须带 `idempotencyKey`
- 由调用方生成，全局唯一
- 服务端记录幂等键与结果
- 重复请求返回首次结果，不重复执行
- 幂等键有效期建议 7 天，可配置

### 8.3 场景

| 场景 | 风险 | 处理 |
|---|---|---|
| 创建销售订单 | 重复创建 | 幂等键去重 |
| 确认订单 | 重复预占 | 幂等键 + 状态机 |
| 发货 | 重复扣库存 | 幂等键 + 发货单号 |
| 采购收货 | 重复入库 | 幂等键 + 收货单号 |
| 库存调整 | 重复调整 | 幂等键 |

## 9. 审计规范

- 所有表包含：`created_at`、`created_by`、`updated_at`、`updated_by`
- 流水表例外：只保留 `created_at`、`created_by`，不可变
- 时间统一 UTC，ISO-8601
- 操作人 MVP 记为 `system`，预留字段

## 10. 错误码规范

- 统一错误码，如 `INSUFFICIENT_STOCK`、`SKU_DUPLICATE`
- 错误响应包含：code、message、details
- 业务异常与系统异常分离
